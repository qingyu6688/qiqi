# 柒柒桌面发布签名说明

维护：maorongkang@gmail.com。适用于 1.1.2 及后续 Windows x64 桌面发布。

## 仓库与更新地址

- 源码和安装包仓库：`qingyu6688/qiqi`。
- 正式发布页：<https://github.com/qingyu6688/qiqi/releases/latest>。
- 更新清单：`https://github.com/qingyu6688/qiqi/releases/latest/download/latest.json`。
- 客户端发布信息：`src-tauri/.env` 中的 `VITE_RELEASE_REPO=qingyu6688/qiqi`。
- 应用标识：`local.qiqi.studio`，更新时不变更。

`src-tauri/tauri.conf.json` 内嵌更新签名公钥，启用 `createUpdaterArtifacts` 和 `requireSignedVersion`。客户端只接受内置公钥验证通过、签名版本与清单版本一致的安装包。公钥可提交到源码；私钥和密码不能提交。

## 两类签名

| 类型 | 作用 | 当前要求 |
| --- | --- | --- |
| Tauri 更新包签名 | 验证更新包来源、完整性和版本，拒绝被替换的包 | 正式发布必须提供 `.sig` 与 `latest.json`，安装前复核 |
| Windows Authenticode 签名 | 向 Windows 标识可信发布者 | 需要受信任的代码签名证书或云签名服务，当前尚未配置 |

更新包签名不会消除 Windows 的“未知发布者”提示。不要用自签证书冒充可信发布者，也不要关闭 TLS 证书校验。将来取得代码签名证书后，应先签署可执行文件和安装器，再生成 Tauri 更新签名；发布后不得修改已签名安装包的字节。

## 私钥与 GitHub Secrets

同一发布渠道应长期使用同一把签名私钥。生成新私钥不能直接替换已安装客户端信任的公钥；更换时必须安排兼容升级。

签名私钥保存在仓库之外的本机受控目录，并保留独立备份。本机密码存于当前用户的 Windows 凭据管理器，签名时短暂读入进程内存，不写明文文件。GitHub 仓库的 Actions Secrets 使用以下名称：

| Secret | 内容 |
| --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | Tauri 生成的加密私钥文本 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 解锁该私钥的密码 |

Secrets 仅供桌面发布工作流使用，不应用于来自不受信任分支的代码执行。禁止在日志打印私钥、密码或用户 API Key。安装包中只包含公钥，不包含签名私钥。

本地构建时，通过当前进程的环境变量提供私钥文件路径或私钥文本，以及对应密码：`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。完成后清除进程内变量。不要把真实值直接写在命令行历史中。

## 版本与发布产物

发布版本在 `package.json`、`package-lock.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 和 `RELEASE.md` 中保持一致。对应 Git tag 为 `v版本号`，例如 `v1.1.2`。

推送版本 tag 后，桌面发布工作流先执行测试和构建，再验证更新清单与安装包签名，随后上传草稿 Release，最后转为正式 Release。不会连带部署 GitHub Pages、Vercel 或 Docker。

`npm run release:prepare -- --tag v版本号` 从 NSIS 构建目录读取安装包和签名，校验通过后将发布文件写入 `release-artifacts/`。公开安装包名使用 `qiqi_版本号_x64-setup.exe`；重命名不改变安装包字节，也不会破坏签名。

每个正式 Release 至少包含：

1. Windows x64 NSIS 安装包（`.exe`）。
2. 同名安装包签名（`.exe.sig`）。
3. `latest.json` 更新清单。
4. `SHA256SUMS` 文件摘要清单。

清单中的版本、Windows 平台下载地址和签名必须指向同一安装包。下载地址限定为本仓库对应版本的 Release 附件。签名的受保护版本字段必须与清单版本一致，仅比较 SHA256 不足以证明发布者身份。

发布前使用 `scripts/validate-desktop-release.mjs` 校验配置、版本、仓库地址、安装包签名和受保护的版本字段。Release 正文取 `RELEASE.md` 中该版本的段落。正式更新源只读取最新正式版，草稿和预发布不会成为常规更新。

## 升级与数据保留

1.1.1 及更早版本没有内置柒柒更新地址，需先下载安装包覆盖升级到 1.1.2 或更高版本。后续通过应用内更新即可继续使用原 API 配置、对话和历史图片。

更新前完整备份安装目录及实际数据目录。自动安装前会等待正在保存的数据写入完成；失败时保留原程序并提示重试。更新安装使用原目录和 `/UPDATE`，不执行卸载清理数据。

下载缓存中同时保存签名和版本。即使重启客户端，安装时也用内置公钥重新检查缓存安装包；缓存文件、签名或版本不一致时拒绝安装并要求重新下载。

本机数据不会上传到 GitHub。发布时只能上传源码和明确列出的构建产物，不上传 `data`、本地备份或配置导出文件。

## 故障处理

- 检查更新失败：检查网络、代理设置和 GitHub 访问情况，确认正式 Release 中存在 `latest.json`。
- 找不到适用安装包：确认更新清单含 Windows x64 NSIS 平台条目。
- 签名校验失败：检查公钥和私钥是否匹配、包是否在签名后被修改、签名版本是否正确；不得跳过验签继续安装。
- 数据保存失败：先解决本地磁盘或写入权限问题，再尝试更新。
- 错发版本：发布更高修订号修复，不覆盖已经发布的同版本安装包和签名。

实际发布与安装验证结果记录在[测试报告](测试报告.md)，不能仅凭配置文件存在就认定发布成功。
